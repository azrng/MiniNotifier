# MiniNotifier 需求文档

> 本文档记录用户侧需求、业务目标与验收口径。设计方案、页面线框图与开发过程记录分别维护在 `doc/design/设计文档.md` 与 `doc/devlog/`。

---

## 1. 项目概述

MiniNotifier 是一个轻量级 Windows 桌面提醒工具，当前核心场景是“喝水提醒”。应用需要以托盘常驻方式运行，在不打断用户工作的前提下，按用户配置的节奏弹出提醒，并提供可持久化的设置、开机自启动、立即提醒、自动更新检测等能力。

产品目标：

- 让提醒工具保持轻量、稳定、低打扰。
- 让核心操作集中在一个简洁设置窗口内完成。
- 让新增、修改、删除或状态变更类操作真实生效并持久化。
- 让发布版本可更新、可追踪、可回滚。

---

## 2. 目标用户与使用场景

### 2.1 目标用户

- 长时间使用 Windows 电脑办公、学习或开发的个人用户。
- 希望有轻量提醒，但不希望提醒工具占用任务栏或频繁打断流程的用户。
- 需要应用在开机后自动进入后台运行的用户。

### 2.2 典型场景

1. 用户启动应用后，应用常驻系统托盘，不主动打断工作。
2. 用户通过托盘或设置窗口查看当前提醒状态、下次提醒时间。
3. 用户设置提醒间隔、弹窗停留时间、是否启用提醒、是否开机自启动。
4. 到达提醒时间后，应用在屏幕右下角弹出喝水提醒。
5. 用户可以手动立即提醒一次，也可以暂停或恢复提醒。
6. 应用启动或用户手动触发时检查是否有新版本。

## 3. 功能范围

### 3.1 托盘常驻

应用启动后应创建系统托盘图标，并以托盘作为主要入口。

需求：

- 托盘悬停提示应能体现应用名称和当前提醒状态。
- 托盘菜单应至少包含：打开设置、立即提醒一次、暂停/恢复提醒、检查更新、退出应用。
- 双击托盘图标应打开设置窗口。
- 退出应用时应释放托盘图标和后台调度资源。

验收：

- 启动后能在系统托盘看到应用图标。
- 通过托盘入口能完成设置窗口打开、立即提醒、暂停/恢复、检查更新、退出。
- 退出后进程不应残留后台提醒调度。

### 3.2 喝水提醒设置

用户应能在设置窗口中管理提醒行为。

需求：

- 支持开启/关闭喝水提醒。
- 支持设置提醒间隔，单位为分钟。
- 支持设置提醒弹窗自动关闭时长，单位为秒。
- 支持开启/关闭 Windows 开机自启动。
- 设置保存后应立即生效并持久化。
- 重新打开窗口或重启应用后，应能看到保存后的设置。

业务规则：

- 默认提醒开启。
- 默认提醒间隔为 30 分钟。
- 默认弹窗自动关闭时长为 15 秒。
- 提醒间隔当前实现允许最低 1 分钟。
- 自动关闭时长应在应用允许范围内校验，非法输入不能保存为有效配置。
- 关闭提醒后不再触发定时弹窗，但托盘和设置入口仍可使用。

验收：

- 修改设置并保存后，界面状态、托盘状态和后台调度同步更新。
- 重启应用后，配置仍保持上次保存结果。
- 配置文件损坏或读取失败时，应用应给出可理解的错误处理或回退策略。

### 3.3 提醒弹窗

到达提醒时间后，应用应显示轻量提醒弹窗。

需求：

- 弹窗显示在屏幕右下角，并避免超出屏幕边界。
- 弹窗包含标题、正文、关闭入口和自动关闭倒计时。
- 弹窗文案应从内置文案池随机生成，并保持轻松、俏皮、非悲伤语气。
- 弹窗应支持手动关闭和倒计时自动关闭。
- 弹窗出现过程应尽量流畅，避免明显卡顿。

验收：

- 到达提醒时间后能正常弹窗。
- 多屏或不同工作区尺寸下，弹窗不应显示到屏幕外。
- 点击关闭后弹窗消失，且下一次提醒仍按规则继续调度。
- 自动关闭倒计时结束后弹窗自动消失。

### 3.4 立即提醒与调度

用户应能主动触发一次提醒，并且调度状态应符合预期。

需求：

- 托盘菜单和设置窗口应提供“立即提醒一次”入口。
- 手动立即提醒后，下次正常提醒时间应重置为当前时间加提醒间隔。
- 定时提醒触发后，应按当前配置重新计算下一次提醒时间。
- 应用应支持单实例，重复启动时不应创建多个托盘、窗口或调度器实例。

验收：

- 点击立即提醒后立刻出现提醒弹窗。
- 立即提醒后，设置窗口显示的下次提醒时间同步更新。
- 多次启动应用不会出现多个托盘图标或多个后台调度器。

### 3.5 开机自启动

用户应能控制应用是否随 Windows 开机启动。

需求：

- 设置窗口提供开机自启动开关。
- 开关状态应真实写入或移除当前用户启动项。
- 不应要求管理员权限。
- 开机自启动状态应持久化并能在设置窗口正确回显。

验收：

- 开启后，系统当前用户启动项中存在 MiniNotifier。
- 关闭后，系统当前用户启动项中移除 MiniNotifier。
- 应用重启后，设置窗口能正确显示当前开机自启动状态。

### 3.6 更新检测

应用应支持自动与手动检测更新。

需求：

- 设置窗口展示当前版本、最新版本、最近检查时间、更新状态。
- 应用启动后可按设置自动静默检查更新。
- 设置窗口和托盘菜单提供手动检查更新入口。
- 发现新版本时，应提示用户确认后再执行更新。
- 自动检查不应自动下载、安装或替换程序。
- 更新源应从现有配置体系读取，不新增平行配置体系。

业务规则：

- 远端版本清单使用 `versions.json`。
- 版本比较应能处理 `1.0`、`1.0.0`、`1.0.0.0` 等等价写法。
- 更新包需要校验下载地址和 Hash；信息不完整时禁止启动更新。
- 更新检查失败不应影响喝水提醒主流程。

验收：

- 手动检查时有 loading、成功、无更新、失败状态反馈。
- 无更新时提示当前已是最新版本。
- 有更新时展示最新版本并提供确认更新入口。
- 更新源不可用或网络失败时，应用仍可正常提醒。

## 4. 非功能需求

### 4.1 平台与技术约束

- 目标平台：Windows 桌面。
- 主技术栈：`.NET 10 + WPF + Wpf.Ui + CommunityToolkit.Mvvm`。
- 架构分层：`View -> ViewModel -> Service -> Repository -> Model`。
- 本地配置优先使用 JSON 持久化。
- 外部配置优先复用 `Microsoft.Extensions.Configuration` 和现有 `appsettings.json`。

### 4.2 体验要求

- 主界面左上角必须展示应用图标和应用名称。
- 设置窗口应简洁清晰，避免无意义层级。
- 所有可见按钮和菜单项必须具备真实交互，不允许只有展示效果。
- 页面和弹窗应有克制但清晰的动效。
- 操作成功或失败应有明确反馈。

### 4.3 稳定性要求

- 应用应支持单实例运行。
- 后台调度不应因单次弹窗失败而崩溃。
- 配置读取、保存、更新检查、更新启动失败时，应保留可恢复路径。
- 退出应用时应释放托盘、定时器、窗口等资源。

### 4.4 持久化要求

- 用户配置必须持久化到本地。
- 新增、变更、删除、开关状态变化等业务操作必须真实生效。
- 重新进入页面、重新打开窗口或重新启动应用后，应能看到已生效状态。

### 4.5 发布要求

- 发布包应可追踪版本。
- 优先复用现有打包与 GitHub Release 流程。
- 生产发布优先采用单文件发布。
- 发布产物不应包含密钥或本地私有配置。

## 5. 页面与入口清单

| 页面 / 入口 | 主要用途 | 必备状态 |
| --- | --- | --- |
| 系统托盘图标 | 后台常驻入口、快捷操作 | 正常、提醒暂停、退出中 |
| 托盘菜单 | 打开设置、立即提醒、暂停/恢复、检查更新、退出 | 正常、操作失败 |
| 设置窗口 | 管理提醒、开机自启动、更新检测 | loading、empty、error、no-permission、正常 |
| 提醒弹窗 | 展示喝水提醒和倒计时 | 正常、自动关闭、手动关闭 |
| 软件更新区域 | 查看版本并检查更新 | 未检查、检查中、无更新、有更新、失败、无权限 |

## 6. 数据与配置

### 6.1 本地提醒配置

应至少保存：

- 提醒是否启用。
- 提醒间隔分钟数。
- 弹窗自动关闭秒数。
- 开机自启动状态。
- 上次提醒时间。
- 下次提醒时间或可推导下次提醒时间的数据。
- 自动检查更新开关。
- 最近检查更新时间。

### 6.2 更新配置

应至少支持：

- 更新渠道名称。
- 远端版本清单地址。
- 当前应用版本。
- 最新版本信息。
- 更新包名称、下载地址、Hash、发布时间。

---

## 7. 验收总则

交付时至少应确认：

- 应用可构建。
- 应用可启动。
- 托盘入口可用。
- 设置保存可持久化。
- 提醒调度和立即提醒可用。
- 开机自启动开关真实生效。
- 更新检查入口可用，并且失败不影响主流程。
- 文档、任务状态和开发记录已同步更新。
